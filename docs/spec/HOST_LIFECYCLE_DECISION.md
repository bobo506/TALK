# 宿主生命周期与多项目资源治理（2026-11-08 用户确认）

本文记录用户与协调者确认的宿主（role_service_host）生命周期目标、当前实例策略、安装包/多项目阶段的治理顺序与验收口径；实现以任务包为准，本文不单独构成开工授权。

## 现状（实测）

- **一个 runtime 绑定一个项目**：`talk-runtime.json` 的 `project_id` 为单值；多项目在现模型下对应多个 runtime。
- `reconcile_hosts` 对**所有已绑定角色**拉起宿主（不论角色 running/stopped），宿主随 runtime 启动而存在。
- 每个角色宿主 ≈ venv launcher 2MB + 解释器 11–13MB ≈ **13–15MB**；当前 7 个宿主合计约 90MB。
- 宿主默认轮询间隔 `DEFAULT_POLL_INTERVAL_SECONDS = 1.0`；桥/CLI 子进程只在角色启动时运行，是重负载。
- 2026-11-08 API 事故根因是 binding 读取**持有 DB 会话时同步探测 WorkBuddy ACP（最长 60s）**，不是宿主轮询；该问题已由性能片修复（探测移出会话、SSE 进线程池、healthz 并发安全、连接池 30+30 应急）。

## 2026-11-13 用户决定：当前实例改为“周期内保留宿主”

- 一个 runtime 启动到停止为一个周期。
- 本周期内只要角色启动过（手动/自动/全部启动），即使随后关闭角色，也**保留其宿主到周期结束**；runtime 正常停止时统一 drain。
- runtime 重启后**不自动拉起宿主**；仅勾选“随项目自动启动”的角色在启动激活中拉起宿主并启动角色。
- 未在本周期启动过的角色没有宿主；启动时按需拉起（宿主冷启动约 2–5 秒，可通过启动请求立即拉起/预热缓解）。
- 宿主异常退出：角色 running/pending 才重试拉起；角色 stopped 不重拉。
- 待定：崩溃后仍存活的外部宿主，角色已停止且未勾选时是否终止（建议终止）；窄宿主（K2.8/DeepSeek）是否同规则；宿主/角色数量上限。
- 不改变 claim/ownership/generation/启停守卫；删除/归档角色终止宿主。
- 本文 2026-11-08 的安装包/多项目 P1–P3 策略保留；当前实例先按上述周期策略实现。

## 目标策略

### 当前开发实例（`prj_e8fe7066bbec`）

- 采用 **A：常驻宿主 + provision 完成预热**；首启 `to_claim` 目标 1–2s。
- 角色数量保持可控（活跃角色个位数到十几个）；暂不引入空闲退出。

### 正式安装包 / 多项目阶段

- 采用 **B/C：按需宿主 + 停止后空闲退出**（或常驻 + 空闲 TTL 退出），稳态只为运行中/近期使用的角色付资源。
- 降低空闲轮询：1s → 2–5s 或指数退避；进一步支持批量/长轮询，合并每宿主请求。
- 单 runtime **软上限 + LRU**：宿主数超限驱逐最久未用，避免无限增长。
- 多项目优先“**每项目独立 runtime + 独立 DB/端口**”（天然分片），不让一个 runtime 扛所有项目；共用 DB 时按项目限流与连接预算。
- 连接池按实测调，不盲目放大（SQLite WAL 单写者，池大只增加排队）。

## 分阶段

| 阶段 | 内容 | 前置 |
|---|---|---|
| P0 | 当前实例：provision 预热宿主（首启领取 ~1–2s） | 可靠性片通过后单独小片 |
| P1 | 宿主按需启动 + 空闲退出 + 软上限/LRU（安装包前置） | P0 实测数据 |
| P2 | 轮询退避/批量 poll + 宿主/请求指标 | P1 |
| P3 | 多项目 runtime/DB 分片与连接预算 | P2 + 多项目需求确认 |

## 不变项与边界

- 不改变 launch claim/report CAS、ownership、generation 与角色隔离语义；不伪造 ready。
- 停止/恢复守卫、忙任务与残余领取保护保留；空闲退出必须保证停止/恢复可证明。
- 预热与按需二选一或折中（预热 + 空闲 TTL），不默认让所有项目角色永久常驻。
- 任何启停、删除、所有权解除仍按现有授权与生产操作门禁执行。

## 验收口径

- 指标：稳态宿主数、总 RSS、每宿主请求频率、API p95、DB 等待/池占用、首启 `to_claim` 与 `claim_to_report`。
- 回归：legacy/workspace 角色 start/stop/delete、恢复守卫、连接池不耗尽、healthz 稳定。
- 30 个宿主（单项目 30 角色或 10 项目 × 3 角色）为压力基线：稳态 RSS、req/s、DB 写排队须在可接受范围；不达标不得宣称安装包可多项目。
