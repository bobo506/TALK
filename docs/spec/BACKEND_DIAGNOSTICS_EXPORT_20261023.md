## 实现与协议

`bridges/backend_diagnostics.py`复用原诊断writer的独立run、lease和分段，以完整项目ID的SHA256划分独立目录。`backend:project`只是存储命名空间，不注册/冒充业务角色。每条网络记录为`kind=backend_event`，明确`component=api/runtime/provision_worker`以及`attribution=project_shared/role`；实际角色仅在`context.member_id`，不改成记录的来源身份。

采集默认关闭，`[backend_diagnostics]`须同时指定`enabled=true`、绝对本地`root`、与实际请求Session/API引擎精确相同的绝对`database_file`和显式`projects`列表。空根/UNC/无效配置/错库不启用；配置读取/日志故障不接管任何服务。API在lifespan内创建、记录启动/就绪/退出/失败及30秒心跳；关闭后禁止后台心跳重新创建writer。统一入口和worker随原流程记录启动/关闭、宿主原Popen退出码、配置发现/处理失败与有限状态。记录不会改变原worker结果、重试、启停或归属守卫。

API仅对已认证、已匹配的项目路由且认证数据库一致时记录请求事件。角色上下文须由认证Session查当前项目的ProjectRole/ProjectAgent历史行后产生可信状态，middleware不使用路径member_id原值；无效角色404/403只能留下项目共享的路由模板/状态。记录变更请求、失败请求和≥5秒的慢读请求，避免高频正常轮询制造大量副本。`X-TALK-Request-ID`由服务生成，关联事件中的request_id，不信任来访同名头；异常由原异常处理栈返回，不能保证其500响应附有此头。路由只存代码模板；原始URL/查询值/头/正文不入新流。后台启动/健康/本机宿主及清理启动异常按显式部署项目共享记录，不能伪称某角色失败。

异常只保存类型、有限调用栈（文件名/函数/行号）和有限原因链。最多64帧/单异常、8层原因链，省略消息/源代码/局部变量，截断明确标记；异常结构采集本身失败时保留有限降级标记。已知worker错误码保留，未知错误码只存摘要；请求key只存`request_key_sha256`。不开放私有原始输出，不读取角色原生会话。

- 项目后台接口：`GET /api/projects/{project_id}/backend-logs/export?since=...&until=...`，格式`talk-backend-diagnostics-export-1`。
- 原角色下载仍为`GET /api/projects/{project_id}/roles/{member_id}/runtime-logs/export?since=...&until=...`，启用后将项目共享/该角色后台事件与原角色事件按时间合并，保持`talk-diagnostics-export-1`和原scope。文件首行增加`backend`扫描/覆盖说明，后续新增`backend_event`类型；消费者应按kind区分。
- 沿用human-only、无Key401/Agent403、项目存在及原角色历史检查；认证/目标检查先于读日志。后台接口绑定实际请求Session的数据库，不能用默认全局引擎误读另一个库的来源。
- 原角色来源不可用但后台可用时，已存在角色仍可下载后台，明确`role.available=false`/`unavailable_records`；后台缺失/错误不丢掉已导出的角色证据。联合导出已正确启用/绑定时，来源全缺返回200部分结果，不能据空文件声称无异常；未开启/错库未绑定则保持原角色入口兼容行为，原来源不可用仍503，不伪造空下载（320的OBS1已据此澄清）。
- 第二次网络投影必须使用请求Session查询的真实项目角色/历史名册集合及当前应用代码定义的路由模板集合，不能仅凭TOKEN/路径正则确认归属。未知member/route即`projection_failed`，既不输出其值，也不把无效角色降为共享身份；角色过滤遇到非法member会进入投影拒绝流程，不能悄悄混过。非HTTP调用须显式提供可信集合，缺省不信任任何持久角色/路由值。
- 时间必须带时区，半开区间`[since,until)`且≤31天。合并共享10秒读取/投影预算、最多10000条、总16MiB（含meta），后台只用角色导出剩余预算；文件/读取字节也扣除先前扫描（verify文件数保守扣两遍）。网络投影继续使用已审查的安全扫描器/第二遍核验/字段脱敏，不透传持久化原对象。

## 完整性与保留边界

扫描是否完整与历史是否完整分开。新流无法证明上线前输出、崩溃空档或未归属请求已全部采集，因此保守固定`history_complete=false`及`backend_coverage_unverified`，整体`complete=false`；这不等于扫描失败。还会明确列出本次时间范围没有输出的组件`backend_missing_components`、扫描/投影/容量/时间等原因。前台沿用“日志文件不完整”提示，仍允许下载证据，不把部分零条解释为没有异常。

全局无项目路由（例如只有task_id的接口）、未认证请求不猜项目，不纳入项目后台导出；既有私有API/launcher输出保持原处且不开放。本片不承诺捕获原生运行器输出/所有异常全文，也不宣称完整日志整项完成。后续如需覆盖这些来源，须先确定可验证归属和最小脱敏字段。

新增后台根只分段，不自动删除（manifest保留天数0；256MiB为每run软提示，8MiB分段），不扩大现有五范围30天/1GiB每日清理策略。其它范围的清理注册仍待另片确认，不能称后台新根已有30天清理。源/元数据/lease继承writer能力，未新建网络上传或数据库表。
