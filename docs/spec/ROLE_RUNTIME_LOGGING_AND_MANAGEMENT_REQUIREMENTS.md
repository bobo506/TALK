## 1. 完整异常日志必须持久留存

- TALK接入桥、接单循环、CLI执行与受管宿主的关键异常需要完整诊断记录：时间（含时区）、异常类型、异常消息、完整traceback及异常因果链。即使str(exc)为空，也必须能识别异常类型和调用位置，不能只留下task queue worker failed:。
- 日志带项目、member_id、实例、进程、task_id或launch_id等实际可得关联标识，以及发生阶段/操作、退出码、超时/取消类别、有效预算等必要上下文。执行预算、HTTP预算与MCP读取等待分别记录，未知字段如实标明，不能从模板推断实际运行参数。
- 详细记录本机持久保存，进程/服务退出、重启后仍可定位原故障；日志上报或状态回报再次失败时，原始异常与后续失败都要保留，不能因二次异常丢掉第一现场。按角色/实例及任务关联，旧/新实例可以追溯，历史记录不被新状态无痕覆盖。
- Key、token、认证信息及敏感配置先脱敏；公共页面/MCP继续只给必要摘要和可追溯日志引用，不默认回灌完整日志、提示词、配置或环境。日志不纳入Git，访问沿已有项目/角色权限边界。
- 实施设计须明确存放位置、定位入口、轮换/保留期限与容量上限；本次没有指定固定天数或容量。清理和轮换应可追踪，不随服务重启直接抹去故障记录。

## 2. 旧角色统一迁入受管服务

- 统一目标覆盖本项目旧角色，包括Codex、Kimi、DeepSeek、旧K2.8等现有CLI接入角色；后续与新角色使用同一套宿主管理、服务状态、启动/关闭和日志关联。
- 迁移保留原member_id、项目归属、业务配置/绑定与历史任务/消息/成果关联。补齐受管所需项目角色和宿主配置，按现有私有凭据/权限规则处理必要接入材料，不通过删除重建角色替代迁移，不追改旧任务快照或改变既有模型选择。
- 在角色空闲、在途任务已完成或妥善处理后，正常退出旧外部启动入口，再由宿主启动并持有新的受管进程，避免旧脚本和新宿主重复运行同一角色。沿既有所有权规则，不凭一个PID或磁盘文件强行接管/结束未知进程。
- 每个运行器核验实际启动配方、原生配置/登录与隔离能力、本人身份、项目/模型alias、进程及实例的launch关联。受权登记和真实启停验收遵守[受管服务合同](ROLE_SERVICE_CONTRACT.md)，未验能力继续如实显示unknown/unverified，不能为了点亮按钮直接标记已受管。
- 迁移后的角色由页面“关闭”确认停止，再“启动”完成手动重启；必须确认关闭实际生效、所有权释放，启动后新实例就绪且能够接单回传，不能只确认两个请求返回成功。
- 与[全角色6小时执行预算](ROLE_EXECUTION_AND_DELETE_REQUIREMENTS.md)一并核对有效参数及旧3600秒覆盖项；仍按单次CLI预算21600、可显式覆盖的合同，不改MCP等待上限。迁移不默认启用随项目启动或无限自动重启。

## 3. 接单健康与恢复边界

- 主进程存活、实例在线、接单循环存活与任务可领取需要可区分的诊断事实。接单循环异常退出或持续不可用应能记录和呈现，不能只凭Python进程还在就宣称服务正常。
- 本次明确手动恢复路径是“关闭完成→启动”。自动重启/退避/重试策略仍需另行设计并遵守在途任务、租约与进程所有权约束；不据本需求直接启用自动恢复、重派任务或恢复失败250。
