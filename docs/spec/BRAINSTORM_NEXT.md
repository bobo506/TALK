# 群聊头脑风暴：下一阶段产品约定

> 2026-09-08 项目管理者确认。状态：方向已确认，尚未实现。本文件用于新窗口恢复与下一切片设计，不代表现有页面已经支持。

## 定义与用户目标

所有面向用户的群聊统一用于头脑风暴，不再提供“普通群聊 / 头脑风暴”类型选择。任务专属 Task Hall 仍承载任务工作流，不受这项群聊定义影响。

用户可以在 Web 群里亲自主持，也可以在正在使用的 Codex、Kimi Code 或 DeepSeek Harness 终端中提出议题，让当前终端里的 Agent 主持会议。会议过程在群中可见，结果回到发起请求的原终端，用户在那里继续工作。

该定义取代早期设计中要求用户选择普通群聊或 brainstorm 的产品交互方向；历史数据迁移和现有内部类型的兼容方案尚待下一切片设计，不在本次分支收尾中修改。

## 两种主持方式

- 人工主持：没有进行中会议时，人类在群中 @所有人 提出议题，成为本轮主持人；负责追问、判断是否需要补充及结束。可以请角色协助汇总，但不因此自动转移主持权。
- 终端 Agent 主持：用户在当前 code 终端明确交办开会，当前 Agent 组织会议、征集其他角色意见、追问和整理分歧，提交正式总结后回到同一终端对话反馈。
- 终端里的主持 Agent 与群中的主持身份必须关联；不能再启动一个独立主持者，让两个同名角色互相触发或重复回答。关联方式属于后续实现设计。
- “返回终端”必须关联原请求 / 原任务上下文，不是只往群里发一条总结，也不是另开一个无关联终端或新对话。

示例：用户在 Codex 交办一个方案议题 → 当前 Codex 主持，邀请 Kimi 和 DeepSeek 讨论 → Codex 整理结论与分歧 → 本段 Codex 对话收到结果并向用户反馈。换用 Kimi Code 或 DeepSeek Harness 时保持相同语义。

## 新群与复用群

- 同项目、基本相同参与团队，默认复用原群；新议题用新一轮会议区分。
- 不同项目、需要信息隔离或明显不同的参与团队，新建群。
- 用户明确要求新群或指定已有群时优先按其要求。
- 一个群同时只允许一轮会议进行，避免交错回复。新一轮在上一轮结束后开始；中途换题必须明确结束当前轮并开始新议题。

## 会议周期与隔离

基本周期：开始议题 → 各角色发表意见 → 主持人追问 / 补充 → 汇总并结束。

- 无进行中会议时，人工 @所有人 发起新轮；已有会议时，再次 @所有人 属于本轮追问，不自动开新轮。
- 每轮有明确的议题、主持人、参与者和状态。开始与结束必须可辨认，不能仅靠消息包含“总结”两字判定结束。
- 人工主持由明确的“汇总并结束”操作收口；终端 Agent 主持由提交正式总结并结束的动作收口。
- 消息、被引用消息、异步角色回复和汇总结论必须绑定原轮。角色读取当前轮所需历史与引用内容，不混入下一轮或其他会议。
- 上一轮的迟到结果不能写入新一轮的上下文或触发新一轮继续讨论。对旧轮消息点击回复也不能悄悄归入当前轮。
- 已结束议题需要继续时，明确开启一个关联的新轮；引用哪些旧轮材料应显式可追溯，不默认混入整个旧群历史。
- 总结应包含结论、未解决分歧、未参与或未回应的角色；角色离线不能导致无限等待。具体等待时长和超时动作尚待设计，不在本次文档中写死。

## 界面与交互

- 显示议题、主持人、讨论中 / 已结束；结束轮次收成可展开的记录，汇总结论优先展示。用户不需要维护内部轮次 ID。
- 回复某个角色应提醒该角色，同时传入被引用内容；同轮与跨轮规则由系统明确处理。
- 保持当前简洁工作台与已验收密度。出现新的可见页面改动时，先给可查看的布局预览，再实现。

## 当前实现与剩余工作

- 已实现：任务闭环、群聊收发、角色接入；TH-7a 提供独立 stdio MCP 八个任务工具与 --check。
- 尚未实现：群聊统一会议语义、普通群聊连续上下文、回复自动提醒、完整轮次隔离、终端主持会议工具、会议总结返回原终端。
- 现有内部 brainstorm 机制仅在特定房间类型及讨论条件下附带有限历史，不能当作上述流程已经完成。既有 talk_terminal_mcp.py 只开放任务工具，不具备开会工具。
