# 统一终端成果回传方案（草案，未授权实施）

日期：2026-09-11。用户要求先设计，不派发开发。覆盖Codex、官方Kimi Code、DeepSeek Harness作为发起终端的场景；模型名称不决定终端职责。

## 已验证与目标

- 当前会话实际talk_list_agents返回1322字符，三个角色各1条实例，仅id/runtime/status/current_task_id/last_seen_at/pid，没有last_error和历史数组；修复已加载。
- 等待/重连/状态检查由普通程序处理，不启动模型回合。只在成果提交、失败或需澄清时投递有界摘要；模型调用量在等待期为0，不承诺整体额度降低的具体比例。
- 结果必须回到发起任务的具体会话，不能只发给agent:codex等成员；同成员多窗口必须隔离。保持人工收取/质量门禁，收到通知不等于任务completed。

## 架构建议

1. TALK通用层：登记已认证终端会话绑定、派发来源、任务状态事件与可补领通知。任务状态及事件持久化应一致，避免完成后通知丢失。
2. 本地终端连接器：模型之外的常驻程序负责订阅/长轮询、离线补领、去重、持久化收件箱和会话忙闲排队。复用通用bridge基础设施，不将规则写死在codex_bridge.py。
3. 运行时适配器：Codex、Kimi、DSH分别实现绑定/验证会话、提交摘要、检测接收确认及忙闲。只有能力验证通过才标为自动续接；普通MCP通知不自动等于客户端会触发模型。
4. MCP入口：派发时由可信连接器附加来源会话绑定；模型无需反复传入完整历史。保留查询/人工收取作为诊断及降级路径。

## 最小数据与流程

- 来源绑定：服务端认证成员、project_id、endpoint_id、runtime、原生session/thread_id、本地工作区标识及连接代次。一个member可绑定多个endpoint。会话ID不能替代鉴权；跨项目/跨账号投递必须拒绝。回调目标只用本地已登记适配器，不接受成果正文指定的命令/任意URL。
- 派发：来源先绑定，创建任务时关联origin。离线/无法自动续接时明确返回manual能力，不默默另建会话。
- 执行：原执行bridge提交成果。TALK生成含event_id、task_id、状态版本、result_message_id的通知，不附带整段对话/旧实例日志。
- 等待：本地连接器在模型回合之外等待，允许程序轮询但无模型推理。断线保留游标并补领；结果拉取继续按任务权限校验。
- 投递：给原会话有界摘要及结果引用（建议每项最多2KB；正文按需取）。忙碌时入队，默认不打断用户。多项结果可合并通知，不能串项目。
- 确认：持久化收件箱接收与运行时接收分开记账；按endpoint+event_id去重，采用可重试投递，不承诺跨进程崩溃下天然严格一次。运行时无幂等确认时不能盲目重发启动模型，须对账或转人工待确认。
- 通知ack只说明送达；审查、接受和collect_result仍走原工作流。自动续接只能推进已授权范围，不能自动增加切片/跨越验收。

## 推进顺序（仅建议）

1. 先做三种终端原会话回传能力验证，使用固定测试通知，不开发业务、不自动派发下游；区分支持/不支持/需TALK启动包装器。未能接回当前Desktop不能算Codex端完成。
2. 确认接口后落最小来源绑定+持久通知+单终端投递链；共用接口为另外两种终端预留，不绑定模型身份。
3. 接入其余适配器，再验证断线补领、重复事件、忙碌排队、同成员多会话隔离、关闭会话、权限变化、通知与收取分离。
4. 指标：等待期模型启动次数=0；一次新成果正常情况下触发一次续接；重复事件不重复触发；真实结果回原会话。记录模型实际用量（如有），不用5小时额度百分比推测token。

没有修改功能代码、没有启动服务/新会话，没有派发开发任务。此方案待用户讨论确认。
