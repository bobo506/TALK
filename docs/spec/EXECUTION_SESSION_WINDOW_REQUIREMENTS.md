## 已确认的机制

1. 由任务分配者按工作关联性选择新建执行对话，或让同一角色继续已有对话；例如同一功能的多个切片可以续用。角色不永久绑定单一对话，分配者可以提前换窗。
2. 每个新执行会话的首轮应带入当前完整任务介绍所需的项目背景、角色职责、固定规范、范围/授权边界、交付格式和恢复状态。完整指可独立开工，不要求复制整个项目历史。
3. 同会话后续轮次只发送本次任务和变化内容；未变化的项目介绍、固定规则、基础合同与统一交付说明不再作为新指令重复注入。任务号、当前目标、基线变化、授权范围变化及验收差异仍须明确；约束变化须补充必要差异或新开会话。
4. 协调角色生成任务内容和bridge拼装执行提示必须一起调整，不能在协调者已写增量后，又由bridge补回固定介绍或全量Hall历史。已有会话历史由原生运行器管理，不把旧记录再次包装成新一轮用户正文。
5. 先确认同功能/工作线和既有作用域/通道，再采用上下文占用作为主标准：可靠占比`<0.60`续窗，`>=0.60`后续指令新窗并恢复完整介绍。可靠占比可得时不设10次硬限；仅单纯缺少可靠指标、同功能/会话/配置可核且有可信完整窗口计数时，备用最多10次交办，第11次新窗。首轮也计，从窗口建立起累计，恢复读数/再次缺数不清零，内部工具调用不计；身份/配置不符、数据矛盾或无可靠计数不能兜底。派发者仍可提前新开。
6. 每个TALK任务仍保留自己的任务号、权限、Task Hall、交付和收取记录。多个任务共用执行会话不合并TALK任务账本；可通过版本化基础合同加本次差异还原完整任务要求，避免要求协调者每轮重新生成重复文字。
7. 用户要求机制写入使用说明；正式上线和人工验收前必须补齐最终用户操作说明，不能只留开发合同。

本次用户方向允许“同功能的不同任务共用执行会话”，优先于287方案里仅考虑同任务修复的候选建议；287关于当前入口、usage未知、权限/并发等实际核查结论保持。首片288开始实现选择/阈值/首轮续轮内核，真实指标与原生会话接线仍在后续，不能把内核自测称为整项已生效。

## 上下文占用的数据与执行边界

- 用户已接受使用DSH界面同类上下文数值作为判断依据，即使包含估算；60%是本次选择的初始策略值，不是经实测证明的最优阈值，不承诺缓存命中或费用改善。
- 本机已安装npm DSH `0.1.5-rc.2`的公开源码可核：`dsh-client-ui-conversation/lib/client.js:15328–15335`的`contextOccupancy`取`projectedTokens ?? pressureTokens`作为使用量，以`contextWindow`为容量；token-meter提供同名会话投影。这里只证明已安装包的数据/显示路径，没有读取桌面当前会话或验证其实际版本/有效配置。
- `projectedTokens`是基于最近用量样本及后续历史变化的预计下一请求上下文量；`pressureTokens`是最近请求报告的prompt侧用量；`contextWindow`是上下文容量。它们不同于会话累计计费token和缓存命中率。
- 自动判断使用原始数值比例`used_tokens / context_window >= 0.60`，不拿UI四舍五入或封顶后的百分数比较，避免59.6%显示为60%就误触发。模型容量、来源/采样时刻、会话及模型身份须可关联；投影分子/分母独立更新，不能默认是同一次请求的原子样本。
- 执行时点建议：每次向已有执行会话投递新任务或后续指令前检查；达到阈值先换窗，再投递完整首轮。当前任务执行中越过阈值不强杀/中断，下一次投递前换窗。60%是续用决策阈值，不是单任务全过程上下文的硬上限；具体投递/取消/并发细则仍须实现合同确认。
- 指标缺失、过期或无法确认来源时保持未知，不填0%。本轮用户已批准仅单纯不可得且有完整可信窗口计数时最多10次兜底；未知身份/配置、非法/矛盾数据、未来/错来源及无可靠计数仍新窗，busy仍先等待。旧288/289当前代码继续未知→新窗，第三片只在隔离候选实现新规则，不称已生效。
- 新窗口首轮还没有历史用量时，按首轮完整流程执行，不因“没有占比”反复创建空窗口；首轮基础包也应保持必要且精简。
- 是否提供阈值配置项、跨运行器指标适配与原生自动压缩后的采样规则仍待具体设计。只复用当前字段不等于TALK已经采到它们；当前headless/bridge尚未传递这些结构化数值。

背景依据：[DeepSeek多轮对话说明](https://api-docs.deepseek.com/guides/multi_round_chat/)说明其Chat Completions请求由客户端携带对话历史；[Anthropic上下文工程说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)强调管理提示、工具和消息历史等有限上下文资源。两份资料及本机源码均不提供“60%最优”的实测结论。

## 使用说明草稿（功能上线后转入用户手册）

以下说明描述待实现的使用方式，当前没有可操作入口，不提供虚构按钮或参数：

- 分配有关联的后续任务时，分配者可以选择继续该角色正在使用的执行对话；新功能或不相关任务可以新开对话。
- 新对话的第一次交办包含必要背景、规则和当前工作状态；继续同一对话时只交代新任务与变化内容，减少反复介绍。
- 同功能的已有对话在可靠占用低于60%时续用，达到60%后下一次交办新对话并恢复信息；可靠读数存在时不受10次限制。仅取不到可靠读数且窗口/配置与完整计数可核时，最多10次交办备用，第11次换窗；轮数从首轮累计，工具调用不计，分配者仍可更早换窗。
- 换执行对话不会丢弃或合并原TALK任务、成果和验收记录；Task Hall仍按任务分别查看。
- 上下文占用包含估算，不代表累计费用或缓存命中；暂时取不到可靠数值时应明确提示，不能显示成0%。同一对话不承诺固定缓存命中率或费用下降。

上线时须按真实入口补充：由谁选择续用/新建、怎样查看当前会话上下文占用及估算/未知提示、达到60%时的反馈、提前换窗/重置的方法、失败和重启后的提示。用户无需理解session id、prompt transport或profile等实现术语。
