## 用户流程

- 人类新建角色并保存配置，宿主完整配置成功后，自动发起该角色的受管启动，直至实际就绪可接任务。
- 用户进一步确认：这相当于系统代替用户自动打开一次角色开关；之后仍可手动关闭或重新启动。新页面不另设默认关闭、需再勾选才启动的选项；旧客户端缺省不启动的兼容规则另行保留。
- 页面保留手动启动/关闭。启动反馈沿用角色列表的一个当前服务状态和详情必要原因，不恢复三状态并排或已删除的配置进度大块。
- 配置完成、启动处理中、实际服务ready分别核实；启动失败保留配置成功事实，显示原因并允许人工重试，不能先显示启动成功。

## 边界

- 只作用以后新建角色的创建成功链路，不能追溯批量启动已有角色；绑定重置/恢复保持现有修复语义。
- 人工关闭优先，页面刷新、重复完成回报、worker重试或旧世代不得反复拉起服务；同一创建来源最多一次有归属的启动意图，沿现有世代/所有权/就绪合同。
- 仍核验真实受管能力、人类授权、身份与配置来源；unverified/unknown或外部会话不绕过门控。能力不足/宿主离线/启动失败要给真实反馈，不伪造运行中或偷偷轮换Key。
- 每角色独立执行实例，复用既有服务持有者和后台启动流程，不能依赖浏览器页面保持打开、不能由短命请求进程泄漏子进程。
- 不扩大为TALK启动时全部角色自启动、无限重启、主动调度生效或其它退出清理能力。
- 保留既有“加载项目时，只启动当前项目已配置且启用自动启动的角色”规划，见[开发路线图](DEVELOPMENT_ROADMAP.md#项目角色配置与自动启动2026-10-04登记后续计划)。这是独立设置/触发，本次首次启动不隐含开启该设置；存量外部/原生入口不自动接管，不能仅凭创建日期、模型名或origin判断可控。
- 人工关闭若先于配置完成回报，也必须阻止该请求随后自动启动；不能只靠启动世代CAS声称人工意图优先。默认初始stopped与实际人工关闭应有可核验的区分。
